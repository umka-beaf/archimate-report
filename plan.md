# План: Docker-сервис для генерации и раздачи Archi HTML-отчётов

Статус: черновик, шаг 0 (планирование). Обновляется по ходу обсуждения.

## 1. Цель

Собрать мультиархитектурный (linux/amd64 + linux/arm64) Docker-образ, который:

1. При старте (и по вебхуку) клонирует/обновляет git-репозиторий с ArchiMate-моделью.
2. Прогоняет модель через `com.archimatetool.commandline.app` (консольный режим Archi) и генерирует HTML-отчёт.
3. Раздаёт получившийся HTML-отчёт статическим веб-сервером (Caddy) на порту 3000.
4. Настраивается полностью через переменные окружения — без ручного вмешательства в контейнер.
5. Публикуется на Docker Hub с настоящим multi-arch manifest list (не «amd64 под qemu»).

## 2. Зафиксированные решения (из обсуждения)

| Вопрос | Решение |
|---|---|
| ARM64 | Свой arm64-образ через **box64**-эмуляцию x86_64 Archi + нативная arm64 JRE. Настоящий dual-arch manifest, без опоры на host-side QEMU binfmt. |
| Формат модели | Поддержать **оба**: одиночный `*.archimate` и **coArchi**-репозиторий (папка с XML-фрагментами). Автоопределение по содержимому репозитория. |
| Обновление отчёта | **Webhook-эндпоинт** для перегенерации по сигналу от git-провайдера (push). Плюс обязательная генерация при старте контейнера. |
| Секреты git | Через переменные окружения: токен (рекомендуется для HTTPS), SSH-ключ (base64/multiline в env), логин+пароль. `*_FILE`-варианты не требуются на первом этапе, но оставляем как возможное расширение. |

## 3. Ключевые находки предварительного ресёрча

- Официальный Archi 5.9.0 **не имеет** нативной сборки под Linux ARM64 — только Linux x86_64, macOS (Intel/Silicon), Windows.
  Источник: https://github.com/archimatetool/archi.io/releases
- Референсный проект [WoozyMasta/archimate-ci-image](https://github.com/WoozyMasta/archimate-ci-image) — **amd64-only**, Ubuntu 22.04 + xvfb + сборка Archi-Linux64. Никакой эмуляции не использует. Полезен как основа для amd64-ветки нашего Dockerfile (список системных зависимостей для SWT/GTK headless-рендеринга: `libgtk2.0-0`, `libswt-gtk-4-jni`, `libxext6`, `libxrender1`, `libxi6`, `libxtst6`, `libcairo2`, `libpango-1.0-0`, `dbus`, `dbus-x11`, `xvfb`).
- **Официальный CLI Archi гораздо мощнее, чем в найденных примерах.** Полный список опций (wiki: [Archi Command Line Interface](https://github.com/archimatetool/archi/wiki/Archi-Command-Line-Interface)):
  - `--loadModel <*.archimate>` — загрузить одиночный файл модели.
  - `--html.createReport <path>` — сгенерировать HTML-отчёт из текущей модели.
  - `--modelrepository.cloneModel <url>` — **встроенный git-клон coArchi-репозитория** силами самого Archi.
  - `--modelrepository.loadModel <path>` — загрузить уже склонированную coArchi-модель из папки.
  - `--modelrepository.userName <name>` / `--modelrepository.passFile <file>` / `--modelrepository.identityFile <file>` — авторизация для клона (HTTP пароль/токен или SSH identity, **из файла**, не из аргумента напрямую).
  - `--csv.export/import`, `--jasper.createReport`, `--xmlexchange.*`, `--script.runScript` — за рамками текущей задачи, но фиксируем на будущее.
  - **Важно:** это значит, что для coArchi-формата нам не нужен свой git-клиент — Archi сделает клон сам. Для «одиночного файла» клон делаем сами (`git clone`), т.к. `--loadModel` не умеет URL.
- Известная проблема: при определённых properties модели генерация HTML отчёта может выдавать пустой `index.html` (0 байт). Issue: https://github.com/archimatetool/archi/issues/980. Взять в тестовый чек-лист.
- Linux CLI по факту требует virtual display даже в headless-режиме (SWT/GTK инициализация) → нужен `xvfb-run` в обеих ветках (amd64 и arm64-через-box64).

## 4. Архитектура сервиса

```
┌─────────────────────────────────────────────────────────────┐
│ Контейнер                                                    │
│                                                                │
│  entrypoint.sh                                                │
│    ├─ 1. Разбор env-переменных, валидация                     │
│    ├─ 2. Подготовка секретов (пишем token/ssh-key/pass во     │
│    │      временные файлы с правами 600, т.к. Archi CLI и    │
│    │      обычный git ожидают файлы, а не значения в argv)    │
│    ├─ 3. Автоопределение формата репозитория                  │
│    │      (обычный git ls-remote + пробный чек / либо clone   │
│    │       и затем смотрим: .git + *.archimate = plain,       │
│    │       .coa файл/model.xml-фрагменты = coArchi)           │
│    ├─ 4. generate.sh — клон/обновление + запуск Archi CLI      │
│    │      под xvfb-run (+ box64 на arm64) → HTML в /data/report│
│    ├─ 5. Запуск веб-сервера Caddy (раздаёт /data/report)       │
│    ├─ 6. Запуск лёгкого HTTP-листенера для вебхука             │
│    │      (POST /webhook → проверка секрета → generate.sh)     │
│    └─ 7. supervisord/tini координирует Caddy + webhook-процесс │
│                                                                │
│  Тома:                                                        │
│    /data/repo    — рабочая копия git-репозитория               │
│    /data/report  — сгенерированный HTML-отчёт (раздаётся)      │
│    /data/secrets — временные файлы секретов (tmpfs предпочт.)  │
└─────────────────────────────────────────────────────────────┘
```

Компоненты процесса внутри контейнера:
- **tini** (или supervisord) как PID 1 — корректная обработка сигналов, два долгоживущих процесса (Caddy + webhook-listener).
- **generate.sh** — идемпотентный скрипт «клонировать/обновить → сгенерировать отчёт → атомарно подменить содержимое `/data/report`» (генерация во временную папку + `rsync --delete` или `mv`, чтобы Caddy никогда не отдавал частично записанный отчёт).
- **webhook-listener** — минимальный HTTP-сервер (варианты обсудим в п.7): принимает POST, проверяет секрет/подпись, кладёт задачу в очередь из одного слота (debounce, чтобы параллельные пуши не запускали генерацию параллельно), вызывает `generate.sh`.

## 5. Стратегия ARM64 (box64)

Основано на найденном у пользователя ИИ-гайде, адаптировано под Docker:

1. Базовый слой arm64-образа: Debian/Ubuntu arm64 + **нативная** arm64 JRE (Temurin 21, как в текущей x86_64 сборке Archi) + `box64` (собранный под arm64 или из apt/репозитория box64, если есть готовый пакет под целевой Debian/Ubuntu — проверить на этапе спайка).
2. Внутрь кладём **x86_64**-дистрибутив Archi как есть (`Archi-Linux64-5.9.0.tgz`), но:
   - Удаляем встроенную x86 `jre/` папку (иначе конфликт/лишний вес).
   - Запуск: `xvfb-run box64 ./Archi -vm /usr/lib/jvm/<arm64-jre>/bin/java -application com.archimatetool.commandline.app -nosplash -consoleLog ...`
3. Гипотеза для проверки: SWT/GTK **native-библиотеки** (`.so`) внутри плагинов Archi собраны под x86_64 (`org.eclipse.swt.gtk.linux.x86_64`). box64 транслирует x86_64-код, поэтому связка «нативный лаунчер x86_64 → box64 → далее весь процесс x86_64 (включая SWT native libs)» должна работать, **если** мы НЕ подсовываем `-vm` с нативной arm64 Java в тот же процесс — иначе получим смешение arm64 JVM + x86_64 SWT native libs, что не взлетит (JNI не эмулируется через ISA-границу так просто).
   → **Решение по умолчанию:** для arm64-ветки НЕ используем `-vm` с нативной Java, а гоняем ВСЁ через box64 (включая x86_64 JRE, идущую в комплекте с Archi). Это медленнее, но корректно с точки зрения ABI. Флаг `-vm` с нативной arm64 Java — это оптимизация, которую пробуем **отдельным экспериментом**, если базовый вариант через box64 будет неприемлемо медленным.
4. Риски:
   - Производительность: генерация отчёта под эмуляцией может быть в разы медленнее, чем нативно на amd64. Для больших моделей (сотни элементов) нужно закладывать таймауты побольше.
   - Совместимость box64 с текущей версией glibc/kernel на целевых arm64-хостах (Raspberry Pi OS, обычные arm64 VPS) — версия box64 должна поддерживать нужные synhronization primitives.
   - Обновления Archi (5.9.0 → следующая версия) не гарантируют, что связка продолжит работать так же — фиксируем версию Archi через build-arg и тестируем при апгрейде.
5. **Точка выхода/переоценки:** если box64-вариант окажется практически неюзабельным (падения/таймауты/несовместимость), откатываемся к плану Б — публикуем только amd64 и документируем, что arm64-хосты должны сами включить binfmt-эмуляцию (`docker run --platform linux/amd64`).

## 6. Работа с git и автоопределение формата модели

Общий вход: `GIT_URL` (обязателен), опционально `GIT_REF` (ветка/тег, по умолчанию — дефолтная ветка).

Алгоритм в `generate.sh`:
1. Подготовить auth (см. §7) → временные файлы (ssh key / pass file), никогда не передавать секрет в argv напрямую (виден в `ps`/`docker top`).
2. Сделать «пробный» `git ls-remote` (или сразу пытаться `--modelrepository.cloneModel`, т.к. он сам делает git-clone).
3. После получения репозитория (или до, по структуре из ls-remote — но проще после первого клона) определить формат:
   - Есть `*.archimate` файл(ы) в корне/на верхнем уровне и **нет** признаков coArchi (`.coa`-файла или служебной структуры model repository) → режим **plain**.
   - Есть coArchi-структура (файл `*.coa` со списком, либо характерная папка-«репозиторий модели» — уточнить на спайке точный маркер) → режим **coArchi**.
   - Если найдено больше одного кандидата `*.archimate` — либо берём по `MODEL_PATH` (env, приоритет), либо берём первый и логируем предупреждение, либо падаем с ошибкой (обсудить: скорее всего — ошибка, чтобы не удивлять пользователя тихим выбором не того файла).
4. Режим **plain**: git clone/pull своими руками (`git` CLI внутри образа) → `Archi --loadModel <path> --html.createReport <out>`.
5. Режим **coArchi**: доверяем клон/загрузку самому Archi (`--modelrepository.cloneModel` / `--modelrepository.loadModel`) с параметрами auth → `--html.createReport <out>` в той же вызове или отдельным шагом (уточнить на спайке — можно ли комбинировать `--modelrepository.*` и `--html.createReport` в одной команде).
6. `MODEL_PATH` (опционально) — явное указание relative-пути к `.archimate`/coArchi-корню внутри репозитория, если автоопределение неоднозначно или репозиторий монорепа с несколькими моделями.

Открытый вопрос для спайка: точный признак coArchi-репозитория в файловой структуре (нужно склонировать реальный пример, посмотреть глазами).

## 7. Контракт переменных окружения (черновик)

| Переменная | Обязательна | Описание |
|---|---|---|
| `GIT_URL` | да | URL репозитория (https или ssh) |
| `GIT_REF` | нет | ветка/тег/коммит, по умолчанию — HEAD дефолтной ветки |
| `MODEL_PATH` | нет | относительный путь к `.archimate` файлу или папке coArchi-модели внутри репо, если авто-детект неоднозначен |
| `MODEL_FORMAT` | нет | `auto` (по умолчанию) / `plain` / `coarchi` — форс-оверрайд автоопределения |
| `GIT_TOKEN` | нет* | HTTPS-токен (PAT). Подставляется в URL или как HTTP-пароль |
| `GIT_USERNAME` / `GIT_PASSWORD` | нет* | логин+пароль для HTTPS |
| `GIT_SSH_PRIVATE_KEY` | нет* | приватный SSH-ключ, base64 ИЛИ многострочный PEM прямо в переменной |
| `GIT_SSH_KNOWN_HOSTS` | нет | содержимое known_hosts; если не задано — `StrictHostKeyChecking=accept-new` с предупреждением в логах |
| `WEBHOOK_SECRET` | нет | если задан — включает и защищает `/webhook`; если не задан — webhook эндпоинт отключён (или открыт — решить, скорее отключён, безопаснее по умолчанию) |
| `WEBHOOK_PATH` | нет | путь эндпоинта, по умолчанию `/webhook` |
| `PORT` | нет | порт раздачи отчёта, по умолчанию `3000` |
| `REGENERATE_ON_START` | нет | `true` (по умолчанию) / `false` — пропустить генерацию при старте (например, если volume с отчётом уже готов) |
| `GENERATION_TIMEOUT` | нет | таймаут на один прогон генерации, сек (важно из-за box64 на arm64) |
| `TZ` | нет | таймзона контейнера |

`*` — из группы «секреты git» должен быть задан ровно один способ авторизации (или ни одного — для публичных репозиториев).

## 8. Вебхук для перегенерации

- Отдельный лёгкий HTTP-эндпоинт (не через Caddy как reverse-proxy на этот же процесс — либо Caddy шлюзует и `/webhook`, и статику, единым портом `PORT`, что проще для пользователя — один порт наружу).
- Caddy настраивается на: `handle /webhook* { reverse_proxy <локальный webhook-listener> }` + `handle { file_server }` для остального (раздача `/data/report`).
- Webhook-listener — кандидаты на реализацию (решить на этапе имплементации):
  - Простейший вариант: небольшой shell+socat/netcat-скрипт — хрупко, не рекомендуется.
  - Микро-сервис на чём-то лёгком, что не тянет за собой доп. рантайм — например, статически собранный Go-бинарник (webhook receiver) или Caddy же с плагином `exec`/встроенным скриптингом.
  - Практичный вариант: **Python** (уже не нужен доп. рантайм, если решим тянуть его для скриптов автоопределения) **или** маленький Go-бинарь, собираемый в отдельном build-stage под обе архитектуры (кросс-компиляция Go тривиальна для amd64/arm64, не требует box64).
  - **Предварительное решение: Go-бинарник** — раз всё равно собираем multi-arch, Go даёт нативный arm64-бинарь без всякой эмуляции для этой части, и это самый маленький/предсказуемый компонент.
- Логика: принять POST → (если `WEBHOOK_SECRET` задан) проверить подпись/токен (поддержать хотя бы GitHub-style `X-Hub-Signature-256`, GitLab-style `X-Gitlab-Token`) → поставить в очередь-однослот (если генерация уже идёт — просто отметить «нужен ещё один прогон после», не плодить параллельные процессы) → запустить `generate.sh` → ответить 202 сразу, не дожидаясь конца генерации (генерация может быть долгой, особенно под box64).
- Дать эндпоинт статуса, например `GET /status` — время последней успешной генерации, идёт ли генерация сейчас, последняя ошибка (полезно для мониторинга).

## 9. Веб-сервер и раздача отчёта

- **Caddy** — единственный входной процесс на `PORT` (по умолчанию 3000):
  - `file_server` на `/data/report` для самого HTML-отчёта.
  - `reverse_proxy` на `/webhook` и `/status` → локальный webhook-listener (слушает на localhost, не наружу).
  - Готовый multi-arch образ Caddy как референс конфигурации (либо ставим caddy-бинарь в наш собственный образ, а не FROM caddy — т.к. нам нужен один финальный образ со всем стеком).
- Атомарность обновления: генерация пишет в `/data/report.new`, по завершении — `rsync -a --delete` или swap директорий, чтобы читатели никогда не видели «наполовину» отчёт.

## 10. Сборка образа

- **Dockerfile** с multi-stage под обе архитектуры, используя `TARGETARCH`/`TARGETPLATFORM` (buildx автоматически прокидывает).
  - Stage `webhook-builder`: golang:alpine (или distroless build) → кросс-компиляция под `$TARGETARCH`.
  - Stage `amd64-archi` / `arm64-archi`: разный набор пакетов и (для arm64) установка box64.
  - Финальный stage: копируем Archi/JRE/box64(если arm64)/бинарь webhook/entrypoint-скрипты, ставим Caddy, git, openssh-client.
- **buildx bake** или GH Actions matrix (`linux/amd64`, `linux/arm64`) → `docker buildx build --platform linux/amd64,linux/arm64 --push`.
- Тегирование: `:<archi_version>`, `:latest`, возможно `:<archi_version>-<image_build_number>`.
- CI: GitHub Actions → сборка на push тега → push в Docker Hub. (Уточнить: у пользователя уже есть Docker Hub аккаунт/организация под это?)
- Публикация README на Docker Hub с описанием env-переменных (копия §7).

5. Нужна ли поддержка нескольких моделей/репозиториев в одном контейнере (сейчас план — один контейнер = один репозиторий = один отчёт; если нужно несколько — это либо несколько контейнеров, либо расширение плана до multi-tenant, что сильно усложняет).
6. Docker Hub: под каким namespace/org публикуем, нужен ли также GHCR как зеркало.
7. Обработка ошибок генерации: если генерация упала — оставляем предыдущий валидный отчёт на месте (не затираем) и отдаём его же плюс индикатор ошибки через `/status`? (Похоже на разумный дефолт — зафиксировать явно.)

## 13. План тестирования (черновик)

- Юнит/скрипт-уровень: `generate.sh` тестируется отдельно от контейнера на тестовых репозиториях (публичный plain, публичный coArchi, приватный по каждому из трёх способов auth).

### 15.4. box64-спайк: Archi НЕ запускается под box64 — не проблема производительности, а поломка OSGi

Собран тестовый образ `archi-box64-spike:test` на базе `debian:trixie-slim` + `box64` + распакованный x86_64 `Archi-Linux64-5.9.0.tgz` (см. Dockerfile ниже). Контекст сборки скопирован на Pi через `scp` (локального Docker/podman CLI в среде агента нет, прямой `DOCKER_HOST=ssh://...` не сработал по той же причине).

Команда:
```bash
xvfb-run -a box64 ./Archi -consoleLog -nosplash \
  -application com.archimatetool.commandline.app \
  --loadModel /data/model.archimate \
  --html.createReport /tmp/report
```

**Результат: процесс не падает, но и не завершается — виснет намертво.**
- В логах контейнера (`docker logs`) — почти сразу после старта (в течение первых секунд) каскад ошибок OSGi:
  ```
  MESSAGE Could not resolve module: com.archimatetool.commandline [7]
    Unresolved requirement: Require-Bundle: org.eclipse.core.runtime; visibility:="reexport"
  ...
  java.lang.IllegalStateException: Unable to acquire application service.
  Ensure that the org.eclipse.core.runtime bundle is resolved and started (see config.ini).
  ```
  То есть под box64 ядро Eclipse (`org.eclipse.core.runtime`) вообще не резолвится, и следом рушится вся цепочка зависимых бандлов (`commandline`, `editor`, `csv`, `widgets`, `jasperreports.commandline`, `zest`, `export.svg`, `help` и т.д.) — Java-приложение фактически не стартует.
  - Похоже на неисправность разрешения/загрузки нативных библиотек (SWT/JNI) под эмуляцией — Eclipse Equinox использует нативный лаунчер для интеграции JVM с OS/GUI-подсистемой, и если что-то на этом уровне работает не так под box64, OSGi framework не может стартовать даже свои чисто Java-бандлы типа `core.runtime`.
- При этом сам процесс (`./Archi ...`, PID под box64) остаётся живым **бесконечно**: проверено через 8–12 минут — `ps` показывает `TIME 00:00:00` (ноль потреблённого CPU-времени за всё это время), состояние `S` (sleeping), `strace -p` подтвердил, что процесс висит в `ppoll(..., NULL, NULL)` — то есть ждёт события, которое никогда не придёт (видимо, нативный лаунчер ждёт JVM-callback, а JVM уже упала с `IllegalStateException` и не может об этом сообщить через сломанный OSGi/JNI-мост). Файл отчёта (`/tmp/report/`) так и не был создан.
- Это **не вопрос "медленно из-за эмуляции"**, а конкретная несовместимость: связка «x86_64 Eclipse RCP native launcher + SWT/GTK JNI-библиотеки под box64» не поднимается вообще. Даже если бы это заработало, тревожный звоночек по производительности всё равно остался бы, но сейчас вопрос ещё более базовый — **запускается ли в принципе**.
- Дополнительно отмечена мелкая проблема самого спайк-Dockerfile: в списке пакетов не было `xauth`, из-за чего `xvfb-run` падал с `xauth command not found` (exit 3) при первом прогоне — исправлено ad-hoc внутри контейнера, но сам файл `spikes/arm64-box64-test/Dockerfile` пока не обновлён (см. открытый пункт ниже).

**Вывод: гипотеза box64 как основной стратегии для arm64 под серьёзным вопросом.** Нужно либо:
1. Копать глубже — попробовать другие версии box64 (RC/edge), другие флаги (`BOX64_DYNAREC`, `BOX64_LOG=1` для диагностики), возможно проблема в конкретной комбинации GTK/SWT-библиотек, которые ставились в спайке (могли быть версии, несовместимые с тем, что ожидает бандлед Archi);
2. Проверить альтернативу из §5 "Plan B" — держать x86_64 JRE эмулируемым, но заменить SWT/GTK-часть или вообще собрать без GUI-зависимостей (маловероятно — Archi CLI всё равно инициализирует SWT display даже для report-режима, это и есть причина требования xvfb);
3. Признать box64-путь нежизнеспособным и откатиться на компромисс: публиковать **честный dual-strategy образ** — arm64-манифест либо (a) вообще не публикуется/явно помечается как неподдерживаемый в v1, либо (b) arm64-ветка запускает build **тем же самым способом** (box64), но документируется как experimental/best-effort, с чётким предупреждением в README, пока проблема не решена;
4. Либо радикальная альтернатива — arm64-ветка вообще не запускает нативный Archi, а даёт понятную ошибку/заглушку "arm64 не поддерживается для генерации, только для раздачи уже готового отчёта" (снижает ценность multi-arch, но честно).

Дальнейшее расследование (пп. 1–2) не проводилось в рамках этого спайка — решено сначала зафиксировать находку и вернуться к пользователю, не тратя больше времени хоста без согласования следующего шага.

**Маркер для автоопределения (обновляет §6 и снимает открытый вопрос №1 из §12):** plain-репозиторий — это один файл `*.archimate` где-то в дереве репозитория; coArchi-репозиторий — это директория, где ЛЮБОЙ уровень вложенности содержит `folder.xml` с корневым элементом `<archimate:ArchimateModel ...>` (без `.archimate`-файла рядом на этом же уровне) и подпапки-категории (`business/`, `application/`, `technology/`, `relations/`, `diagrams/` и т.д., но не обязательно все сразу — зависит от того, какие слои реально использует модель). Практический алгоритм детекции:
1. Ищем `**/*.archimate` в репозитории → если ровно один — plain-режим, используем как `MODEL_PATH`.
2. Если `*.archimate` не найден — ищем `**/folder.xml`, где корневой тег `<archimate:ArchimateModel`, → если найден — coArchi-режим, `MODEL_PATH` = директория, содержащая этот `folder.xml` (не сам файл).
3. Если найдено несколько кандидатов любого типа — требуем явный `MODEL_PATH` от пользователя (как и планировали).

**Дополнительно подтверждено (закрывает открытый вопрос №2 из §12):** `--modelrepository.loadModel <путь-к-папке-модели>` и `--html.createReport <путь>` **прекрасно комбинируются в одном вызове CLI** — не нужно два последовательных запуска. Команда:
```bash
xvfb-run -a ./Archi -consoleLog -nosplash \
  -application com.archimatetool.commandline.app \
  --modelrepository.loadModel "<путь-к-папке-модели-coArchi>" \

```
сработала с первого раза на этой модели (34 view, 1220 xml-файлов элементов/отношений) на amd64: чистый лог `Loaded model: 'GLYCAM-Web'` → `Generating image for View 1..34 of 34` → `Report generated!`, итоговый `index.html` — 317 560 байт, весь отчёт — 16 MB. `--modelrepository.loadModel` тут используется для **локально уже склонированного** coArchi working copy — сам git clone/pull в этом тесте не проверялся отдельно (репозиторий уже был на диске через обычный `git clone`), но раз CLI одинаково понимает путь к папке независимо от того, кто её туда положил (наш собственный git-клиент или `--modelrepository.cloneModel`), для entrypoint-скрипта это не имеет значения — сам git clone можно делать и своими средствами (что и планировали) и просто передавать Archi путь к уже готовой рабочей копии.

### 15.9. box64 глубокий разбор — точная причина краша найдена, upstream-баг открыт, найдена нативная альтернатива (2026-08-19)

По просьбе пользователя ("Я бы копнул box64 глубже. arm64 ветка — отличительная особенность проекта") — продолжили копать после находки §15.4 (тогда был просто бесконечный зависон без диагностики).

**Шаг 1 — более новый box64 меняет картину.** Debian trixie даёт стоковый `box64` 0.3.4. Сторонний репозиторий [ryanfortner/box64-debs](https://ryanfortner.github.io/box64-debs/) публикует пересобранные версии 0.4.3 (июль 2026), в т.ч. **платформо-специфичные варианты** под конкретные SoC: `box64-rpi4arm64`, `box64-rpi5arm64`, `box64-rpi5arm64ps16k`, `box64-rk3588`, `box64-m1` и т.д. Подключили репозиторий вручную (без `curl | bash` — этот паттерн заблокирован классификатором прав Claude Code; вместо этого скачали список/ключ и `apt-get install` отдельными шагами) и поставили `box64-rpi5arm64` прямо на хост Pi (не в контейнер — для быстрой итерации).

С 0.4.3 процесс **больше не зависает** — за ~20.7 сек происходит чистый **SIGBUS**, с полноценным JVM crash-репортом (`hs_err_pid*.log`). Это уже прогресс: есть точная точка отказа вместо тишины.

**Шаг 2 — точная точка краша.** По `hs_err_pid*.log`:
```
C  0x00000000300a0340
j  org.eclipse.swt.widgets.Display.initializeSystemColorsDisabled()V+18
j  org.eclipse.swt.widgets.Display.initializeSystemColors()V+59
j  org.eclipse.swt.widgets.Display.init()V+13
...
```
Крашится JNI-вызов `org.eclipse.swt.internal.gtk.GTK.gtk_entry_new()` — самый первый шаг создания SWT `Display` (он создаёт временный `GtkEntry`, чтобы прочитать системные цвета). Т.е. падение происходит **на границе box64/GTK-wrapper**, а не где-то в логике Archi.

**Шаг 3 — проверили гипотезу про page size (ложный след).** У box64-repo есть отдельный пакет `box64-rpi5arm64ps16k` — специально под ядра с 16K page size. Проверили: `getconf PAGESIZE` на Pi = **16384**, а стоял обычный `box64-rpi5arm64` (4K-вариант). Переустановили на `ps16k`-вариант, повторили прогон под `xvfb-run` — **краш идентичен**, тот же PC (`0x00000000300a0340`), тот же стек. Несовпадение page size — не причина в данном случае.

**Шаг 4 — правильный флаг для полной эмуляции GTK найден.** `BOX64_NOWRAPPER` (что пробовали в §15.4/до этого шага) — **несуществующая опция**, ничего не делает. Реальная опция называется **`BOX64_NOGTK=1`** — отключает box64-механизм "wrapped" (проброс вызовов в нативную ARM64-библиотеку хоста вместо полной эмуляции x86_64-версии). С `BOX64_NOGTK=1` поведение действительно меняется — box64 пытается грузить **x86_64**-версии `libgtk-3.so.0`, `libgdk-3.so.0`, `libglib-2.0.so.0` и т.д., которых просто нет на arm64-хосте (только нативные ARM64). Т.е. флаг рабочий, но чтобы им воспользоваться, нужно самим поставить x86_64-сборки GTK-стека рядом (тяжеловесный путь, отдельно не проверяли — см. открытый вопрос ниже).

**Шаг 5 — это открытый, непочиненный баг апстрима box64.** Нашли почти точное совпадение: [ptitSeb/box64#2850](https://github.com/ptitSeb/box64/issues/2850) — тот же класс приложения (DBeaver = Eclipse SWT/GTK3 + Java), тот же краш в момент инициализации SWT `Display`, тоже упирается в `g_type_class_ref`/glib-wrapper на границе box64. Issue помечен тегами `pagesize` и `wrapper`, **открыт**, без подтверждённого фикса или воркэраунда от мейнтейнеров на момент проверки.

**Вывод по box64-ветке:** проблема не в конфигурации box64 и не в конкретной сборке — это структурный, известный upstream-баг в механизме "wrapped"-библиотек box64 применительно к связке JVM+SWT+GTK3. `BOX64_NOGTK=1` теоретически обходит его ценой полной x86_64-эмуляции GTK, но требует притащить x86_64-сборки всего GTK3-стека (glib, gobject, gdk-pixbuf, pango, cairo, gtk3) — не проверено, жизнеспособность неизвестна, риск новых несовместимостей.

**Шаг 6 — альтернатива: собрать Archi нативно под linux/arm64, без box64 вообще.** Официальных ARM64 Linux-сборок Archi нет ([archi.io/releases](https://github.com/archimatetool/archi.io/releases): только Linux64, Win64, Mac Intel/Silicon), но:
- Есть свежая попытка в nixpkgs — [NixOS/nixpkgs#550840](https://github.com/NixOS/nixpkgs/pull/550840) ("archi: init at 5.9.0") — **собирает Archi 5.9.0 из исходников** через `maven.buildMavenPackage` (Tycho, JDK 21, профиль `-Pproduct`), а не берёт готовый tgz. Но итоговый `meta.platforms = [ "x86_64-linux" ]` — **тоже только x86_64**.
- Причина видна в корневом `pom.xml` апстрима (`archimatetool/archi`, ветка `release_5.9.0`) — Tycho-плагин `target-platform-configuration` явно перечисляет ровно 4 target environment: `win32/win32/x86_64`, `linux/gtk/x86_64`, `macosx/cocoa/x86_64`, `macosx/cocoa/aarch64`. **`linux/gtk/aarch64` в списке нет** — хотя `macosx/cocoa/aarch64` есть, т.е. Eclipse SWT для linux.gtk.aarch64 в принципе существует в p2-репозиториях (Eclipse IDE официально даёт linux-aarch64 сборки), просто Archi его не запрашивает.
- **Гипотеза (не проверена):** если добавить `<environment><os>linux</os><ws>gtk</ws><arch>aarch64</arch></environment>` в этот список и пересобрать Tycho-продукт — есть шанс получить **нативный** ARM64 Linux Archi без box64 вообще. Это решило бы проблему полностью и дало бы честную производительность вместо эмуляции, но требует: (а) форка/патча Archi или сборки с оверрайдом pom.xml, (б) полноценного Maven/Tycho-тулчейна (JDK 21, интернет к p2-репозиториям Eclipse), (в) отдельной проверки, что все зависимости (GEF, JFace и т.д.) реально резолвятся под linux.gtk.aarch64.

**Открытый вопрос пользователю:** какое направление предпочтительнее для arm64-ветки —
1. Родная сборка Archi под linux/arm64 из исходников (Tycho, добавить environment) — выше усилия, но правильное решение без эмуляции;
2. Долбить box64 дальше (`BOX64_NOGTK=1` + притащенные x86_64 GTK-библиотеки) — неопределённый исход, тяжеловесно, обходит известный open-баг;
3. Для arm64-хостов использовать amd64-образ под QEMU full-system/binfmt эмуляцией (просто, гарантированно работает, но медленнее и не "честный" arm64, от чего изначально хотели уйти);
4. Отложить arm64 совсем, выпустить сначала только amd64.

### 15.10. Спайк: нативная сборка Archi под linux/gtk/aarch64 из исходников (2026-08-19, в процессе)

Пользователь согласился попробовать вариант 1 из открытого вопроса §15.9 — родную Tycho-сборку.

- Склонировали апстрим `archimatetool/archi` (тег `release_5.9.0`) в `spikes/archi-source/` (не коммитим — свежий апстримный клон, добавить в `.gitignore`).
- В корневом `pom.xml` временно заменили список `<environments>` на один `linux/gtk/aarch64` (было 4 платформы: win32/x86_64, linux/x86_64, macosx/x86_64, macosx/aarch64) — чтобы спайк собирался быстрее и проверял именно интересующий нас таргет.
- Maven 3.9.9 скачан вручную в scratchpad (без `apt-get` — нет root/sudo в этом окружении).
- Запущена сборка: `mvn -B -P '!tests,product' -Dproject.build.outputTimestamp=... clean verify`, лог — `spikes/archi-source-build-logs/build.log` (не коммитим, сырой build-лог).

**Результат сборки: BUILD SUCCESS.** Все ~25+ модулей реактора (включая `com.archimatetool.editor.product`) собрались за **3 мин 26 сек**, без единой ошибки резолва p2-зависимостей — гипотеза из §15.9 (шаг 6) подтвердилась с первой попытки: p2-репозиторий Eclipse 2024-06 действительно содержит SWT/GTK-фрагменты под `linux.gtk.aarch64`, Archi их просто никогда не запрашивал. Артефакт — `com.archimatetool.editor.product/target/products/Archi-linux.gtk.aarch64.zip` (~114 МБ, также распакован рядом в `.../linux/gtk/aarch64/Archi/`).

**Проверка подлинности сборки** — `file` на лаунчере и на всех 7 нативных `.so` из `org.eclipse.swt.gtk.linux.aarch64_3.126.0.v20240528-0813.jar` (включая `libswt-pi3-gtk-4965r11.so` — именно ту библиотеку, чей `gtk_entry_new()` крашился под box64 в §15.9) подтвердил: все бинарники — настоящий `ARM aarch64` ELF, не x86_64.

**Сквозной тест на реальном железе (Raspberry Pi 5, 192.168.1.18) — УСПЕХ.**
- Артефакт перенесён на Pi (`scp`, ~120 МБ tar.gz) и распакован в `/root/box64-quick-test/native-arm64/Archi/`.
- Обнаружен и устранён недостающий рантайм: на хосте вообще не было Java (`java: command not found` — предыдущее box64-тестирование работало на x86_64 JRE, вшитом в старый `Archi-Linux64-5.9.0.tgz`, а этот нативный Tycho-продукт свой JRE не бандлит). Поставлен `openjdk-21-jre-headless` через обычный `apt-get` (на Pi есть root, в отличие от sandbox-окружения агента) — подошла версия 21.0.12, штатный ARM64-пакет Debian trixie.
- Первая попытка запуска через `-application.args --loadModel,...,--html.createReport,...` (comma-joined, как в box64-варианте из §15.4) завершилась тихим `exit 0` **без генерации отчёта и без записи в `.archi/.metadata/.log`** — то есть OSGi-приложение либо не стартовало, либо не получило аргументы. Переключились на формат из проверенного amd64-запуска (§14): `--loadModel` и `--html.createReport` как **прямые top-level аргументы** самому `./Archi`, а не упакованные в `-application.args`. С этим форматом всё сразу заработало:
  ```bash
  xvfb-run -a ./Archi -consoleLog -nosplash \
    -application com.archimatetool.commandline.app \
    --loadModel /root/box64-quick-test/model.archimate \
    --html.createReport /root/box64-quick-test/report-native
  ```
- Чистый лог: `[Core] Loaded model...` → `[HTMLReport] ...` → `Generating image for View 1 of 1` → `Report generated!`, exit 0.
- Отчёт валиден: `index.html` — 6585 байт (побайтово тот же размер, что и на amd64-baseline из §14 на той же тестовой модели), PNG-диаграмма реально отрисована, весь отчёт — 2.0 МБ. **Никакого краша, никакой эмуляции — честный нативный ARM64 рендеринг SWT/GTK через xvfb.**

**Итог: нативная сборка Archi под `linux/gtk/aarch64` полностью рабочая альтернатива box64**, снимает open-баг апстрима box64 (§15.9, шаг 5) целиком, а не обходит его. Закрывает открытый вопрос §15.9 — см. решение ниже.

**Обновление открытого вопроса из §15.9:** вариант **1 (родная сборка)** подтверждён на практике и рекомендуется как основной путь для arm64-ветки. Варианты 2 (глубже долбить box64) и 3 (QEMU-фоллбэк) сняты с рассмотрения — родная сборка одновременно проще в обслуживании (нет upstream-бага, за которым нужно следить) и быстрее (без эмуляции). Открытым остаётся только вопрос **как** это встраивать в Dockerfile — см. технический долг ниже.

### 15.11. Открытые технические долги от этой сессии

- Тест на модели Archisurance (313 элементов) не проводился ни под box64, ни на нативной ARM64-сборке — стоит перепроверить на нативной сборке (box64-ветка сама по себе больше не в фокусе, см. 15.10), т.к. в §15.9 отмечалось, что тест не окончательный без модели с properties (баг #980).
- **Не решено:** как встраивать нативную Tycho-сборку (§15.10) в Docker-пайплайн для arm64-ветки — два варианта: (а) Dockerfile сам делает multi-stage Tycho-сборку из исходников на этапе `docker build` (тяжелее/медленнее сборка образа, но всегда актуальная версия Archi, ничего заранее не публикуется); (б) собрать артефакт один раз отдельно (как в этом спайке) и опубликовать/закешировать его, Dockerfile просто скачивает готовый zip. Также нужно решить: возвращать ли `pom.xml` к полному списку из 4 target environments (win32/x86_64, linux/x86_64, macosx/x86_64, macosx/aarch64) плюс добавленный `linux/gtk/aarch64` — если сборка встраивается в CI навсегда, лучше форкнуть/патчить апстрим правильно, а не оставлять список урезанным, как в спайке (см. комментарий в патче `pom.xml`).
- На хосте Pi (192.168.1.18) убраны box64-специфичные следы: пакеты `box64-rpi5arm64`/`box64-rpi5arm64ps16k` (`apt-get purge`), сторонний apt-репозиторий и ключ `ryanfortner/box64-debs` (`/etc/apt/sources.list.d/box64.list` + ключ) удалены. **Ещё не убрано** (оставлено намеренно, на случай повторной проверки, например на модели Archisurance): `openjdk-21-jre-headless`, директория `/root/box64-quick-test/` (`native-arm64/` с распакованной нативной ARM64-сборкой Archi, `report-native/`, `model.archimate`, старые box64-crash-логи, `xvfb99.log` и т.д.). Убрать это тоже нужно будет, когда линия исследований на этом хосте закроется полностью.
- `spikes/arm64-box64-test/Dockerfile` использует стоковый Debian `box64` 0.3.4 — устарел вдвойне: не отражает находки про board-specific пакеты 0.4.3 **и** box64-путь в целом больше не рекомендуемое направление (см. 15.10). Кандидат на удаление/замену нативным Tycho-подходом, а не на обновление.

**Вывод для плана:** базовый сценарий (M1, amd64 MVP) подтверждён технически рабочим и несложным — можно приступать к Dockerfile для amd64-ветки без дополнительных исследований. Для arm64-ветки вопрос "работает ли вообще честный нативный рендеринг на этой архитектуре" **закрыт положительно** (§15.10) — box64-эмуляция как основной путь отклонена в пользу нативной Tycho-сборки под `linux/gtk/aarch64`, сквозной тест (загрузка модели → HTML-отчёт с PNG-диаграммой) пройден на реальном Raspberry Pi 5 без единой ошибки. Остаётся открытым только инженерный вопрос интеграции в Docker-пайплайн (см. технический долг в §15.11), а не вопрос принципиальной работоспособности. Пункт про coArchi-структуру на реальных данных с properties (баг #980) по-прежнему требует отдельной проверки — переносится на начало работы над M2/M4.
