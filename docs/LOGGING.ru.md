# Логи: LOG_LEVEL

🇬🇧 [English](LOGGING.md) · 🇷🇺 Русский

---

### Единая схема на три отдельных процесса

`entrypoint.sh`, `generate.sh` и `archi-webhook` (Go-бинарник) пишут в один и
тот же поток `docker logs`, поэтому у них общий формат и общее правило
фильтрации, а не своё изобретение у каждого:

```
<UTC-таймштамп в RFC3339> [component] LEVEL message
```

Пример: `2026-09-06T16:34:30Z WARNING [webhook] rejected: bad signature (provider=generic, slug="")`

`component` — это `entrypoint`, `generate` (или `generate:<slug>` в
[multi-model режиме](MULTI_MODEL.ru.md)), либо `webhook` (`webhook:<slug>`
для строк по конкретной модели). Собственный консольный вывод Archi CLI
(`[HTMLReport] ...`) и собственные JSON-логи Caddy оставлены как есть — это
не «наши» процессы, переформатировать или фильтровать их не нужно, схема
касается только трёх перечисленных процессов.

### `LOG_LEVEL` — одна переменная, четыре уровня

| Уровень | Когда использовать |
|---|---|
| `DEBUG` | Пока не используется ни одной строкой в проекте — зарезервирован под будущую детальную трассировку |
| `INFO` (по умолчанию) | Обычные рабочие сообщения: старт, прогресс клонирования/генерации, успешная публикация |
| `WARNING` | Восстановимые проблемы: повторённая git-операция, отклонённый вебхук-запрос, упавшая стартовая генерация одной модели в multi-model режиме (контейнер продолжает работать) |
| `ERROR` | Фатальные проблемы: неверная конфигурация, генерация, упавшая и остановившая весь контейнер |

`LOG_LEVEL=WARNING` скрывает строки `INFO` (шум старта/прогресса), оставляя
всё, что действительно требует внимания. Невалидное значение (что угодно,
кроме четырёх перечисленных) — жёсткая fail-fast ошибка при старте, тот же
паттерн, что и у невалидного `WEBHOOK_PROVIDER`:

```
2026-09-06T16:34:39Z [log] ERROR LOG_LEVEL must be one of DEBUG, INFO, WARNING, ERROR, got: TRACE
```

По умолчанию, если не задано — `INFO`.

### Заметки по реализации

- Shell-сторона (`entrypoint.sh`, `generate.sh`, `docker/lib/model-config.sh`)
  использует одну общую библиотеку, `docker/lib/log.sh`: она валидирует
  `LOG_LEVEL` один раз при сорсинге и экспортирует `log_debug`/`log_info`/
  `log_warn`/`log_error`. Каждый сорсящий её скрипт заранее выставляет свою
  переменную `LOG_COMPONENT` (например, `"generate:myslug"`), которую
  библиотека читает, чтобы подставить тег `[component]`.
- Go-вебхук не может сделать `source` bash-файла, поэтому
  `docker/webhook/main.go` реализует ту же валидацию и ту же фильтрацию по
  четырём уровням нативно (`initLogLevel()`, `logDebug`/`logInfo`/`logWarn`/
  `logError`) — сохраняя прежнюю конвенцию: тег `[webhook]`/`[webhook:slug]`
  встраивается как обычный текст внутрь сообщения, а не как отдельное поле.
- `initLogLevel()` выполняется самым первым выражением в `main()` Go-бинарника
  — раньше всего, что потенциально может залогировать ошибку (например,
  невалидный `MODEL_<N>_SLUG`) — фильтр по уровню должен быть готов ещё до
  первого возможного вызова лога.
