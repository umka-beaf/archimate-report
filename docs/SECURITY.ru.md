# Безопасность: аутентификация и авторизация

🇷🇺 Русский · 🇬🇧 [English](SECURITY.md)

---

### Сервис сам не аутентифицирует посетителей

Нигде в проекте нет ни логина, ни API-ключа, ни модели пользователей. Это
осознанное решение: предполагаемый деплой уже стоит
за реверс-прокси с forward-auth (Caddy + Authentik, в конфигурации, для
которой этот дизайн писался), и правило авторизации по path — естественный
инструмент для [multi-model режима](MULTI_MODEL.ru.md), где разным
стейкхолдерам может быть нужен доступ к разным моделям. Встраивание второго,
дублирующего слоя авторизации прямо в контейнер только создало бы два места,
которые нужно держать синхронизированными, и два места, где может
спрятаться неправильная настройка.

### Рекомендуемая схема: Caddy/Authentik forward-auth по path

```caddyfile
example.com {
    @needs_auth not path /*/webhook
    handle @needs_auth {
        forward_auth authentik:9000 {
            uri /outpost.goauthentik.io/auth/caddy
            copy_headers Remote-User Remote-Groups Remote-Email Remote-Name
        }
    }
    reverse_proxy archimate-report:3000
}
```

Любые дополнительные правила авторизации по path (например, требование
конкретной группы Authentik для `/finance-model/*`) — целиком дело вашего
прокси и вашего identity-провайдера, у этого проекта нет своего мнения на
этот счёт, кроме одного: «не сломайте вебхук» (см. ниже).

### Критично: не заворачивайте `/<slug>/webhook` под общий auth

Git-провайдеры (GitHub, GitLab, ...) шлют вебхук-запросы напрямую — они
никогда не проходят через ваш SSO-флоу логина, поэтому forward-auth-правило,
применённое ко всему `/<slug>/*`, молча превратит каждый вебхук в
`401`/редирект на страницу логина, и отчёт просто перестанет обновляться без
явной ошибки на вашей стороне (см. [docs/WEBHOOK.ru.md](WEBHOOK.ru.md) о том,
как выглядит здоровый вебхук-запрос). `/<slug>/webhook` уже защищён своей
собственной проверкой `WEBHOOK_SECRET` — ему не нужен, и он не должен иметь,
общий proxy-уровневый auth перед собой. С `/<slug>/status` — вопрос выбора:
он не раскрывает содержимого модели, только статус генерации, поэтому вполне
разумно оставить его открытым рядом с вебхуком, если так проще для вашей
схемы.

### Общий `WEBHOOK_SECRET` на все модели — принятый компромисс

У сервиса один владелец (см. [docs/MULTI_MODEL.ru.md](MULTI_MODEL.ru.md)), поэтому один секрет
вебхука и один `WEBHOOK_PROVIDER` действуют на все модели одного инстанса —
отдельного секрета на модель нет. Если нужны криптографически разные
секреты по моделям (например, потому что разные команды владеют разными
апстрим-репозиториями и не должны иметь возможность триггерить
регенерацию друг у друга), заводите отдельные инстансы контейнера, а не
рассчитывайте, что этот проект разграничит доверие внутри одного инстанса.

### Что НЕ считается угрозой в этой модели

- Кто-то угадывает slug модели и напрямую заходит на `/<slug>/` — заглушки
  на `/` и `/<slug>/` (см. [docs/MULTI_MODEL.ru.md](MULTI_MODEL.ru.md))
  избегают *рекламирования* списка slug'ов, но это защита от случайного
  обнаружения, а не гарантия невозможности связать URL с моделью. Реальный
  контроль доступа (forward-auth правило выше) должен стоять перед всем, что
  действительно чувствительно.
- Любой, у кого есть `WEBHOOK_SECRET`, может триггерить регенерацию *любой*
  модели инстанса, не только «своей» — это прямое следствие дизайна с общим
  секретом выше и причина рекомендации «отдельные инстансы для отдельных
  границ доверия».
